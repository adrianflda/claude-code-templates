## blocker

- [critic] **EARS-H2b / EARS-H4b; Gherkin 'A second, later heading that also says "Invariants" never overrides the first match'; INV-12** — The only test offered for the duplicate-heading tiebreaker uses a 'later heading' `## 9. Changelog` whose BODY merely contains the sentence "Invariants were tightened in review." — the heading text itself is 'Changelog', which does not match EARS-H2's pattern at all. So no Gherkin scenario or invariant (including INV-12, 'a fixture with two "Invariants"-matching headings (second one inside prose)' — again prose, not a heading) ever constructs two headings that BOTH genuinely match EARS-H1/H2's rule, and EARS-H4b (duplicate id in the same table) has no test at all. An implementation that resolves real duplicate matching headings/ids the wrong way (e.g. last-match-wins, or merges both sections) passes every check this contract defines. _(suggestion: Add a fixture/scenario with two headings that both literally match EARS-H2 (e.g. '## 6. External Observable Invariants' and a later '## 12. Additional Invariants'), assert only the first's table is used; add the same for EARS-H1 duplicates and for EARS-H4b (two rows of the same table yielding the same bare id).)_
- [critic] **Invariants table / §3 QA procedure step 6-8 vs INV-1, INV-14** — §0 states the real failure happened because breaker-gate.mjs's internal call to contract-lint.mjs blocks before breaker-invoke.mjs is ever reached ('blocked-invalid-contract ... before breaker-invoke.mjs is ever reached'). Yet every breaker-gate.mjs check in this contract (INV-9, INV-10, INV-11, the write-failure/stale-record Gherkin scenarios, §3 steps 6-8) runs against the LEGACY `fixtures/m2/contracts/example.md`, and every check of the numbered-heading fixture (INV-1, INV-14) calls `breaker-invoke.mjs` or `contract-lint.mjs` directly, never through `breaker-gate.mjs`. No test ever runs `breaker-gate.mjs --contract contract-1045-shape.md` end-to-end. A fix applied correctly to `contract-lint.mjs` and `breaker-invoke.mjs` in isolation, but wired incorrectly (or not at all) inside `breaker-gate.mjs`'s own call sites, would pass every check here while still reproducing the exact original bug when actually run the way the ticket observed it. _(suggestion: Add an INV/Gherkin scenario that runs `breaker-gate.mjs --contract contract-1045-shape.md ...` end-to-end (with a passthrough --breaker stub) and asserts it reaches the breaker instead of exiting at `blocked-invalid-contract`.)_

## major

- [comprehension] **§1.0 / "The `gate` field" bullet; also Gherkin / "A later passing breaker clears the stale not-executed record"** — The term "referee gate" ("a passthrough of the referee gate's own `gate` value when the run never reaches the breaker (L35)") and the phrase "modulo the referee/contract-lint gates" are used without any definition. There is no Glossary entry or inline explanation of what the referee gate is, what values it can produce, or how it relates to `breaker-gate.mjs`. _(suggestion: Add a Glossary entry for "referee"/"referee gate" or state explicitly that it is out of scope and just name the pass-through behavior without needing the reader to understand its internals.)_
- [comprehension] **EARS-V4, step (3)** — Step 3 bundles three distinct sub-checks — "EARS-V0's method/command sets, origin checks, EARS-V6/V6a's Host rule" — into a single ordered step. If a vector violates more than one of these simultaneously (e.g. an invalid HTTP method AND a bad Host header), the contract does not say which sub-check's reason is reported, so two implementers could report different reasons for the same dropped vector. _(suggestion: Give an explicit sub-order for step 3 (e.g. key/command-set checks, then origin checks, then Host rule), or state that any one failing reason may be reported without further specificity.)_
- [comprehension] **EARS-V4, step (4)** — Step (4) is a per-vector rule evaluated by `runVectors`/`validateVectors` in `vector-breaker.mjs`, but it depends on knowing "whether the `--probe` CLI argument... was not given" to `breaker-invoke.mjs` — a separate process/module. The contract never specifies how this fact reaches `runVectors` (e.g. a function parameter, an env var, a field on the vectors object), and no Gherkin scenario or INV row exercises this rule, so an implementer has no concrete signature or test to anchor the plumbing to. _(suggestion: State the parameter/field `runVectors` receives to know whether a probe command was supplied, and add a Gherkin scenario or INV row exercising step (4).)_
- [critic] **External Observable Invariants / INV-3, INV-4, INV-12** — These three probes are specified as 'node -e script loading `buildBlindInput` from `breaker-invoke.mjs` ... printing JSON.stringify(invariants)' — a direct import of an internal function, not an observation of the CLI's stdout/exit code/files. INV-1 and INV-2 show the externally-observable alternative is easy (feed the --breaker stub the blind input and have it echo back what it saw). As written, INV-3/4/12 are predicates over internal state, contradicting the table's own 'External Observable Invariants' framing, and they silently require `buildBlindInput` to remain an importable, identically-shaped export — an implementation detail nowhere else mandated by this contract. _(suggestion: Rewrite INV-3/4/12 the same way as INV-1: have the --breaker stub print back the relevant parsed fields (e.g. the EO-6 entry) in its verdict JSON, and assert on breaker-invoke.mjs's own stdout.)_
- [critic] **EARS-H2 / EARS-H2b vs EARS-H3** — EARS-H3 says a heading nested deeper than the section-opening heading (level > N) is swallowed into that section's body, not treated as a new section. EARS-H2/H2b's matching rule, however, is stated as applying to 'a contract' with no exemption for headings already inside another section's body. A `###` heading nested inside the QA-procedure section that happens to lexically match 'Invariants' (e.g. a QA sub-step titled '### Known invariants to recheck') would, by EARS-H2b's literal 'first such heading in document order' rule, be picked as the Invariants section opener — contradicting EARS-H3's claim that it is QA-procedure body content. No criterion resolves this ordering/precedence conflict. _(suggestion: State explicitly that section-opening headings are found only among headings not already swallowed by an earlier-opened section's body (i.e. resolve section boundaries before running the H2/H2b pattern match), or add a worked example showing the intended behavior.)_
- [critic] **EARS-V6; Gherkin 'A Host header matching the system's own registrable domain is accepted, not dropped'** — EARS-V6 has two independent accept branches: (a) Host value exactly equals the systemUrl's own hostname, (b) Host value ends with '.<registrable-domain>'. Every 'accepted' scenario/invariant (the only passing-Host Gherkin scenario, using `develop.mbvs-server-development.example.com` against hostname `mbvs-server-development.example.com`) exercises branch (b) only; branch (a) — a vector setting `Host` to exactly the system's own hostname with no subdomain — is never tested anywhere in this contract. _(suggestion: Add a scenario/invariant where a vector's Host header is set to exactly the systemUrl's hostname (no subdomain) and assert it is accepted.)_
