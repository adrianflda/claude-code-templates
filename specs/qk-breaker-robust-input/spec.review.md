# Contract review — specs/qk-breaker-robust-input/spec.md

**BLOCKED** — 2 blocker, 7 major, 1 nit.
Blind reviewers saw only the contract text. Resolve each blocker in the contract, or waive it explicitly at the intention gate.

## blocker

- [critic] **EARS-H6 / Gherkin 'empty QA-procedure' & 'empty invariants' scenarios / INV-5, INV-6** — EARS-H6 requires naming BOTH sections 'when both are empty simultaneously... never only the first one found,' but every scenario and invariant that exercises H6 empties only ONE section at a time (QA-procedure-only in one scenario/INV-5, invariants-only in the other/INV-6). No scenario empties both sections together and checks the reason names both. An implementation that always reports only the first empty section it finds (violating the explicit 'never only the first one found' clause) passes every check this contract defines. _(suggestion: add a scenario/invariant with both the QA-procedure body and the invariants table blanked, asserting the reason contains both 'qaProcedure' and 'invariants' literally.)_
- [critic] **EARS-V4 / Gherkin 'Scenario Outline: One per-vector-invalid vector is dropped and reported'** — EARS-V4 pins a fixed evaluation order across five independent rule classes and states the system stops at 'the first failing rule.' Every example in the only scenario testing this ('host', 'origin', 'anchored') constructs a vector that violates exactly one rule class. No scenario or invariant constructs a vector violating two rule classes at once (e.g. an unknown key AND a bad Host) to confirm precedence is actually honored. An implementation that reports whichever violated rule it happens to check first (ignoring the mandated order) passes every check this contract defines. _(suggestion: add one scenario with a vector violating e.g. both rule (1) (unknown key) and rule (5) (bad anchor id) and assert only rule (1)'s reason is reported.)_

## major

- [comprehension] **§0.1 fixtures list / `vector-author-prompt.test.mjs` description** — The contract states this file "reads the real `breaker/vector-author.md` via a **relative** path (`../../../breaker/vector-author.md`)". Counting from the test file's own directory (`plugins/quality-kernel/scripts/fixtures/qk-breaker-robust-input/`), three `../` lands at `plugins/quality-kernel/breaker/vector-author.md`, not `plugins/quality-kernel/scripts/breaker/vector-author.md` — the location you'd expect given that `breaker-claude.mjs` and the other scripts this contract targets all live directly under `scripts/`. The contract never states `breaker/vector-author.md`'s full path anywhere else (it is always written bare), so a reader cannot independently confirm which directory the coder must edit to satisfy EARS-V8/INV-13. _(suggestion: State the full repo-relative path of `breaker/vector-author.md` explicitly once (e.g. in §1.0's vocabulary list or the Glossary).)_
- [comprehension] **EARS-M6 and its Gherkin scenario "A breaker command that exits non-zero is INSTRUMENT-BROKEN" (`--breaker "exit 3"`)** — Several scenarios/invariants pass `--breaker` values that only work if the string is executed through a shell: `"exit 3"` is a shell builtin, not an executable, and the various `--breaker "node -e \"...\""` examples embed quoting that only resolves correctly if a shell parses the argument string into argv. The contract never states that `breaker-invoke.mjs` spawns the `--breaker` string via a shell (e.g. `spawn(cmd, {shell: true})`) rather than splitting it naively or exec'ing the first token directly. An implementer who spawns without a shell would see `exit 3` fail as "command not found" (still `INSTRUMENT-BROKEN` per EARS-M6, but the reason would not contain "3" as the Gherkin requires), silently failing that acceptance check. _(suggestion: Add to §1.0's vocabulary that the `--breaker` argument is executed through a shell (name which one, e.g. `/bin/sh -c`), so the exact failure-reason wording is reproducible.)_
- [critic] **EARS-H6 / INV-5, INV-6 / Gherkin empty-section scenarios** — EARS-H6 requires the reason to list 'every ##/### heading line found in the contract, verbatim, in document order,' but INV-5/INV-6 and their Gherkin siblings only assert the reason 'contains' the one heading belonging to the emptied section. No check confirms unrelated headings (e.g. '## 1. EARS acceptance criteria') are also listed, or that order is preserved. An implementation that lists only the current section's heading passes every check. _(suggestion: assert the reason (or a structured field) contains every `##`/`###` heading line from the fixture, in order, not just the emptied section's own heading.)_
- [critic] **EARS-V6a(b) / Gherkin Host-header scenarios** — EARS-V6a(b) specifically defines the IPv6-bracket-literal case (`^\[.*\]$`, e.g. `[::1]`) as requiring exact-match Host checking, called out by name in the rationale as closing a host-impersonation bug class. No Gherkin scenario or Invariant exercises an IPv6-literal `systemUrl` (only dotted-quad IPv4 and single-label `localhost` are tested). An implementation that forgets the bracket branch (e.g. only checks the dotted-quad regex) passes every check. _(suggestion: add a scenario with systemUrl `http://[::1]:9000` and a Host header like `evil.::1` or `[::1].evil.net`, asserting it is dropped.)_
- [critic] **EARS-H4 (malformed bold clause)** — EARS-H4's 'IF only one side of the cell carries `**`... THEN... leave the stray `**` characters in place' clause has no scenario or invariant anywhere exercising an unmatched-bold id cell (e.g. `**EO-9 | x | y` or `EO-9** | x | y`). An implementation that strips any leading/trailing `**` regardless of pairing — the opposite of what's required — passes every check this contract defines. _(suggestion: add a fixture row with one-sided `**` and assert the id is extracted with the stray markers intact (or that extraction fails in the documented way).)_
- [critic] **EARS-M5 (removal-failure branch)** — EARS-M5 covers failures of directory creation, temp-file write, rename, AND removal, but QA step 8 / the 'write failure' Gherkin scenario only exercises the write path (an `INSTRUMENT-BROKEN` run with a read-only `.quality-kernel`). No scenario makes the directory unwritable for an EARS-M3 *removal* (a `BREAKER_PASS`/`FAIL`/`INDETERMINATE` run with a pre-existing stale record and a read-only directory), so the 'removing the record fails' half of EARS-M5 is untested. _(suggestion: add a scenario: pre-seed breaker-not-executed.json, chmod the directory read-only, run a passing-breaker stub, and assert the exit code/gate are unaffected and the failure is logged to stderr.)_
- [critic] **Carried to design / EARS-V4 step (4) bullet** — The 'Carried to design' section states 'no scenario/INV exercises step (4) at all,' but the Gherkin already contains 'Scenario: An HTTP vector with no expect is dropped when no --probe was given (EARS-V4 step 4)' which does exercise it. This is a factual contradiction inside the contract that could mislead the coder/designer about what is and isn't already covered (the valid remaining point — no parameter/field is named for how the probe-given fact reaches `runVectors`/`validateVectors` — is a separate, still-real gap). _(suggestion: correct the carried-forward bullet to drop the false 'no scenario exercises it' claim and keep only the real gap: the missing parameter/field name for the probe-given signal.)_

## nit

- [comprehension] **EARS-H4b ("two or more rows of the SAME invariants table")** — "Table" is never defined — if the recognized invariants section's body contains more than one markdown table (e.g. separated by prose or a sub-heading), the contract does not say whether duplicate-id handling (EARS-H4b) applies within each table separately or across the whole section. _(suggestion: Either state that a section is assumed to contain exactly one table, or define where one table ends and another begins (e.g. a non-`|`-prefixed line breaks it).)_
